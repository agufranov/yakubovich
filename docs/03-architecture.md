# Архитектура

## Принцип

Главный риск проекта — не нагрузка, а **хрупкость 10-20 коннекторов к чужим сайтам,
которые ломаются молча**. Архитектура подчинена этому: изоляция источников, сохранение
сырых данных, наблюдаемость каждого коннектора.

Нагрузка при этом смешная: десятки тысяч активных лотов, сотни тысяч в год. Это
уверенно один сервер и один Postgres. Никаких Kafka, Kubernetes и микросервисов —
они здесь только удорожают.

## Слои данных

```
   Источники              raw                staging              core                выдача
 ┌───────────┐      ┌─────────────┐     ┌────────────┐     ┌────────────┐     ┌────────────┐
 │ ГИС Торги │─┐    │ как пришло  │     │ разобрано  │     │ единая     │     │ Next.js    │
 │ ЭТП #1    │─┼───▶│ JSONB       │────▶│ по своей   │────▶│ модель     │────▶│ SSR/ISR    │
 │ ЭТП #2    │─┤    │ + хеш       │     │ схеме      │     │ lot/asset  │     │ + API      │
 │ …         │─┘    │ неизменяемо │     │ источника  │     │ дедуп      │     │            │
 └───────────┘      └─────────────┘     └────────────┘     └────────────┘     └────────────┘
```

**raw — неизменяемый.** Сохраняем ответ источника как есть, с хешем и временем. Это
не паранойя, а рабочая необходимость: правила нормализации будут меняться каждую
неделю первые полгода, и переразбирать надо из сырья, а не ходить к источнику заново
(источник уже удалил лот / забанил / изменил формат). Хеш дает бесплатное определение
«изменилось ли» — не трогаем staging, если ответ идентичен предыдущему.

**staging** — разбор в схему конкретного источника, один к одному с его полями.
Здесь живет вся его специфика и кривизна.

**core** — единая модель, по которой работает сайт. Только сюда смотрит фронтенд.

Разделение staging/core стоит недорого, а окупается на втором же источнике: без него
логика второй площадки протекает в модель первой, и дальше это не расшить.

## Контракт коннектора

Каждый источник реализует один интерфейс. Всё остальное — расписание, ретраи,
метрики, сохранение raw — делает платформа, а не коннектор.

```ts
interface Connector {
  code: string;                                    // 'gis-torgi', 'etp-rts', …

  // Что появилось/изменилось. Отдает лишь идентификаторы — дешевый обход.
  discover(cursor: Cursor): AsyncIterable<{ externalId: string; cursor: Cursor }>;

  // Полная карточка по идентификатору. Возвращает сырой ответ.
  fetch(externalId: string): Promise<RawPayload>;

  // Сырое -> схема источника. Чистая функция, без сети. Так она тестируется
  // на сохраненных фикстурах и переигрывается на всём архиве.
  parse(raw: RawPayload): StagingLot;
}
```

Три требования, каждое из практики:

1. **`parse` — чистая функция.** Никакой сети внутри. Тогда её можно прогнать по всему
   `raw` при изменении правил и покрыть тестами на реальных фикстурах.
2. **`discover` отделен от `fetch`.** Обход списка дешевый, забор карточек дорогой.
   Разделение позволяет ежедневно обходить всё, но забирать только изменившееся.
3. **`cursor` — курсор источника**, а не «дата последнего запуска». Для ГИС Торги это
   срез `biddType × регион × окно дат` (обход потолка в 10 000, см.
   [research/gis-torgi-api.md](research/gis-torgi-api.md)).

## Наблюдаемость: обязательна с первого дня

Коннектор, который сломался, обычно не падает — он тихо возвращает 0 записей. Поэтому
на каждый источник пишем метрики и **алертим на аномалии, а не на исключения**:

- лотов получено за прогон / из них новых / изменившихся
- доля ошибок парсинга, доля лотов с пустыми обязательными полями
- время последнего успешного прогона

Правило тревоги: «источник X дал сегодня на 80% меньше обычного» — это и есть главный
сигнал поломки. Исключения ловит Sentry, но молчаливую деградацию — только это.

Плюс страница `/admin/sources` со статусом каждого источника. Дешево и снимает
основной операционный риск.

## Поиск

Начинаем на Postgres: `tsvector` с русской конфигурацией + `pg_trgm` для опечаток,
GIN-индексы, фасеты обычными `GROUP BY`. На объемах в сотни тысяч лотов этого хватает
с запасом, а отдельный поисковый движок — это ещё один сервис, который надо
разворачивать, синхронизировать и чинить.

Выносить в Meilisearch/OpenSearch — только когда упремся: миллионы документов или
фасеты медленнее ~200 мс. Заранее закладываем абстракцию поискового репозитория,
чтобы переезд был локальным изменением.

## Чего сознательно нет

| Не делаем | Почему |
|---|---|
| Kubernetes | Один сервер. Docker Compose решает всё, что нужно |
| Kafka / RabbitMQ | BullMQ на Redis, объемы на три порядка ниже порога |
| Микросервисы | Команда 1-2 человека, монолит + воркеры быстрее во всём |
| Отдельный поисковый движок | Postgres тянет; добавим по факту упора |
| Хранение документов лотов | Терабайты. Храним ссылки, качаем лениво (см. [10-economics.md](10-economics.md)) |
