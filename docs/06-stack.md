# Стек и инфраструктура

## Выбор языка: один, а не два

Рекомендация — **весь проект на TypeScript**.

Соблазн взять Python для сбора данных и TypeScript для сайта понятен (в Python лучше
инструменты парсинга и всё, что связано с ML). Но для команды из 1-2 человек два
языка означают два набора зависимостей, два деплоя, дублирование моделей данных и
постоянные потери на переключении. Сбор данных здесь I/O-bound — это ровно то, в чем
Node хорош, а тяжелого ML в проекте нет: разбор документов при необходимости уходит
в LLM по API, а не в локальные модели.

Исключение, при котором стоит пересмотреть: если понадобится серьезный OCR и разбор
сканов PDF — тогда отдельный Python-сервис только под эту задачу, с общением через
очередь. Не раньше, чем задача реально возникнет.

## Компоненты

| Слой | Выбор | Почему |
|---|---|---|

| Деплой | Docker Compose | Один сервер. K8s тут — чистый расход |

## Хостинг

Российский провайдер (Selectel, Timeweb, Yandex Cloud). Причины, помимо цены:

- **152-ФЗ**: персональные данные граждан РФ хранятся на территории РФ. У нас будут
  учетные записи пользователей и ФИО должников-физлиц ([07-legal.md](07-legal.md)).
- **Сетевая доступность**: источники — российские госсайты и ЭТП. С зарубежных
  адресов часть из них недоступна или отдает 403 (мы это уже видели на Федресурсе).
  Коннекторы должны ходить с российского IP.

Старт: один VPS, 4 vCPU / 8 ГБ / 100 ГБ SSD. Postgres, Redis, web и воркеры в
Compose на одной машине. Это перекрывает нагрузку с многократным запасом.

Первое, что разделяется при росте, — БД на отдельную машину. Не раньше.

## Где живут данные: путь от файлов к Postgres

Вопрос «файлы или бесплатный BaaS» разобран 31.08.2026 с замерами на нашей же
базе. Ответ: файлы сейчас, SQLite потом, Postgres на российском хостинге в
конце. BaaS не рассматриваем.

### Замеры (МЭТС, 31.08.2026)

| | одна запись | на 15 000 лотов |
|---|---|---|
| raw-карточка (HTML) | 191 КБ | **2,8 ГБ** |
| она же в gzip | 47 КБ (4,1x) | ~700 МБ |
| core-лот (то, по чему ищем) | 3,1 КБ | 46 МБ |

Вывод из таблицы: тяжелое у нас — сырье, а не лоты. Core остается маленькими
данными еще очень долго.

### Почему не бесплатный BaaS

**Юридически.** Мы храним ФИО и ИНН должников-физлиц, а персональные данные
граждан РФ обязаны лежать на территории РФ ([07-legal.md](07-legal.md)).
Supabase, Neon, Firebase, Turso — США и ЕС. Это не вопрос вкуса: любой BaaS
для нас сразу сужается до российского хостинга, где бесплатных тиров нет.

**По объему.** Типичный бесплатный тир — 0,5 ГБ. Мы пробиваем его примерно на
семитысячной карточке МЭТС.

**По смыслу.** Решение №5: архив — главный невосстановимый актив. Класть его на
чужой бесплатный тир, который засыпает после недели простоя и меняет условия в
одностороннем порядке, — плохой размен.

### Зарубежный хостинг: проверено и закрыто

31.08.2026 проверялся вариант «сервер товарища за границей» (Хельсинки,
Финляндия, доступ по ssh). Вывод: **не подходит, и решает это не право, а сеть.**

| Источник | Из Финляндии | Из России |
|---|---|---|
| ГИС Торги (`torgi.gov.ru`) | TCP 443 не открывается вовсе | работает |
| МЭТС (`m-ets.ru`) | **403** | 200 |
| iTender (`bankrupt.centerr.ru`) | 200 | 200 |

403 у МЭТС приходит и на ботовый, и на браузерный User-Agent — режут по адресу,
а не по клиенту. То есть **два из трех рабочих источников недоступны**, и
коннекторы за границу не переносятся ни при каких настройках. Обход геоблока
прокси не рассматриваем: хрупко, дорого на наших объемах (15 000 страниц по
200 КБ) и против решения №12 о честной работе с источниками.

Побочная польза: сбор и сырье физически обязаны остаться в РФ, что совпадает с
требованием 152-ФЗ. Спорить с законом не приходится — с ним совпала сеть.

Отдельно про ту конкретную машину: 15 ГБ диска (4.2 ГБ свободно), 1.9 ГБ ОЗУ,
1 ядро, порты 80/443 заняты чужими сервисами. Даже без блокировок класть туда
2 ГБ сырья значило бы забить чужой диск до отказа и уронить чужие сервисы.
**Чужая рабочая машина — не хостинг**, даже когда доступ есть.

### Раскладка по слоям

**raw остается файлами навсегда.** Он append-only, его никогда не запрашивают,
только переигрывают при смене парсера. Это то, в чем файловая система хороша, а
БД плоха: гигабайты HTML в строках Postgres — деньги на ветер. Единственное
требование — **сжимать** (gzip, 4x).

**core: NDJSON -> SQLite -> Postgres.** NDJSON спокойно живет до ~50 тысяч
лотов. Дальше не BaaS и не сразу Postgres, а SQLite: один файл, ноль
администрирования, настоящий SQL и индексы. Интерфейс хранилища уже написан как
репозиторий, замена локальная. Postgres — когда появится сервер, и двигателем
будет не число лотов, а 152-ФЗ и рыночные наблюдения (фаза E, docs/12).

**Дамп для витрины ломается раньше всех остальных.** Каталог на GitHub Pages
качает базу целиком: 831 лот = 2,9 МБ, 15 000 лотов = ~46 МБ на каждого
посетителя. Лечится подрезкой дампа до полей, которые каталог реально
использует (сейчас туда едет лот целиком минус вложения) —
[11-deploy.md](11-deploy.md).

## Обязательное на первый день

**Российский корневой сертификат в образе.** Без него коннекторы не подключатся к
госсайтам. Кладем в Dockerfile, не в инструкцию для человека:

```dockerfile
COPY certs/russian_trusted_root_ca.pem /usr/local/share/ca-certificates/rtrca.crt
RUN update-ca-certificates
ENV NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt
```

Отключение проверки TLS вместо этого — недопустимо. Подробности: [research/grabli.md](research/grabli.md).

**Резервные копии Postgres.** Ежедневный `pg_dump` в объектное хранилище с ротацией.
Ценность проекта — накопленный архив; он невосстановим, потому что источники удаляют
завершенные лоты. Бэкап здесь — не гигиена, а защита основного актива.

**Разумное поведение коннекторов.** Мы ходим на чужие сайты. Ограничение частоты,
экспоненциальные паузы, честный User-Agent с контактом, уважение к `Retry-After`.
Это не только этика: агрессивный сбор кончается баном по IP, а бан по IP — это
остановка продукта.

## Структура репозитория

```
apps/
  web/               Next.js: сайт и публичный API
  worker/            воркеры BullMQ
packages/
  db/                схема Drizzle, миграции
  connectors/
    core/            HTTP-клиент, контракт Connector, тест-хелперы
    gis-torgi/
    etp-*/           по пакету на площадку
  normalize/         категории, атрибуты, регионы, цены, даты
  shared/            типы, утилиты
tools/
  probe/             скрипты разведки источников
docs/
```

Монорепозиторий (pnpm workspaces). Коннекторы — отдельные пакеты с общим ядром: так
у каждого свои фикстуры и тесты, и поломка одного не мешает остальным.

## Тестирование коннекторов

Единственная стратегия, которая здесь работает: **фикстуры реальных ответов**.

`parse` — чистая функция ([03-architecture.md](03-architecture.md)), поэтому сохраненный
JSON-ответ прогоняется через нее в обычном юнит-тесте, без сети. При изменении формата
источником достаточно обновить фикстуру и увидеть, что именно сломалось.

Отдельно — **smoke-тест по расписанию**, который реально ходит в источник и проверяет,
что контракт жив: поля на месте, фильтры фильтруют (методика проверки фильтров — в
[грабли](research/grabli.md)). Он ловит молчаливое изменение чужого API раньше, чем
это заметят пользователи.
