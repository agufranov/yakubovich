# Выкладка на GitHub Pages

Зачем: показать работающий сайт снаружи, не заводя сервер и не платя за хостинг.
Это витрина текущего состояния, а не продакшен — целевая картина по-прежнему
[docs/06-stack.md](06-stack.md) (сервер + Postgres).

## Команда

```
npm run deploy                        собрать статику и запушить в ветку gh-pages
npm run deploy -- --build-only        только собрать, результат в apps/web/out
npm run deploy -- --no-push           собрать и закоммитить, но не пушить
npm run deploy -- --base-path=/repo   если remote еще не настроен
npm run deploy -- --cname=example.ru  свой домен (тогда base-path пустой)
```

Скрипт — [tools/deploy/gh-pages.ts](../tools/deploy/gh-pages.ts). Он собирает
Next в статику, кладет рядом дамп базы, публикует `out/` коммитом в ветку
`gh-pages` через отдельный git worktree (рабочая копия не трогается) и печатает
адрес сайта.

Первый раз: в Settings → Pages репозитория выбрать Source «Deploy from a branch»,
ветка `gh-pages`, папка `/(root)`.

Сборка и dev-сервер делят `apps/web/.next`: запуск `npm run deploy` при
работающем `npm run web` уронит dev-сервер ошибкой MODULE_NOT_FOUND —
перезапустить его после выкладки.

Собирать в CI нельзя: `data/` не в git (решение о том, что архив бэкапится
отдельно), а без данных собирать нечего. Выкладка — с машины, где лежит база.

## Как это устроено

Сайт умеет собираться в двух режимах, код один и тот же.

| | dev / обычный build | `STATIC_EXPORT=1` (GitHub Pages) |
|---|---|---|
| Каталог | фильтрует сервер, браузер получает готовый HTML | фильтрует браузер по дампу |
| Дамп базы | роут `/data/lots.json`, всегда свежий | файл `out/data/lots.json` |
| Карточки лотов | рендер на запрос | 652 страницы отрендерены заранее |
| Файлы лотов | прокси `/api/file/<id>` с кэшем | прямые ссылки на torgi.gov.ru |

Три вещи, которые это обеспечивают:

1. **Дамп базы одним файлом** ([apps/web/lib/dump.ts](../apps/web/lib/dump.ts)).
   В статике каталог фильтрует лоты в браузере — тем же `queryLots` из
   `@bankrot/storage`, которым фильтрует сервер. Реализация фильтрации одна,
   выдача не разъедется (проверяется совпадением счетчиков). Дамп — все поля
   лота, кроме `attachments`: по вложениям не ищут, а весят они треть.
2. **Файлы, которым нужен сервер, называются `*.ssr.ts(x)`, а только для
   статики — `*.static.tsx`**; что подключать, решает `pageExtensions` (см.
   [apps/web/next.config.mjs](../apps/web/next.config.mjs)). Так у страницы `/`
   в каждом режиме ровно одна реализация: серверная
   [page.ssr.tsx](../apps/web/app/page.ssr.tsx) или клиентская
   [page.static.tsx](../apps/web/app/page.static.tsx). Разметка каталога при
   этом общая — [components/Catalog.tsx](../apps/web/components/Catalog.tsx),
   ей все равно, откуда пришла выдача.
3. **Слаг лота вместо id в URL**: `id` — это `sourceCode:externalId`, а
   двоеточие нельзя положить в имя файла. `gis-torgi:1234` -> `gis-torgi--1234`
   (`lotSlug` в [packages/shared/src/slug.ts](../packages/shared/src/slug.ts)).

## Чем за это платим

- **Картинки идут напрямую с torgi.gov.ru.** У кого в браузере нет сертификата
  Минцифры — увидит битые превью. Прокси существовал ровно за этим, но в статике
  прокси невозможен, а тащить оригиналы в репозиторий нельзя: 1964 картинки, до
  6 МБ каждая (следующий шаг — превью в WebP, [docs/08-seo.md](08-seo.md)).
- **Каталог на витрине не индексируется.** Там он рендерится в браузере, и
  поисковику приезжает пустая оболочка. Карточки лотов — полноценный HTML, и
  именно они главный SEO-актив (docs/08); для витрины этого достаточно. В
  продакшене каталог остается серверным, поэтому проблема — только у витрины.
- **Данные обновляются только выкладкой.** Сбор идет локально, сайт узнает о
  новых лотах в момент `npm run deploy`.
- **/sources — снимок на момент сборки**, а не живая наблюдаемость.

## Что едет в дамп

Дамп качает **каждый посетитель**, поэтому его состав — не удобство, а контракт:
тип `QueryableLot` ([packages/storage/src/query.ts](../packages/storage/src/query.ts))
перечисляет поля явно, и компилятор не даст каталогу воспользоваться тем, чего
в дампе нет. Раньше тип был «`CoreLot` минус вложения», и дамп пух вместе с
моделью — каждое новое поле коннектора автоматически ехало в браузер.

Подрезка 31.08.2026 дала **3.1x** (замер на 2703 лотах): 12.3 МБ -> 3.98 МБ,
в gzip 1.65 МБ -> 0.55 МБ. Что убрали и почему:

| Убрано | Было | Почему можно |
|---|---|---|
| `name` и `source` у атрибутов | 1.4 МБ служебного против 0.9 МБ полезного | Подпись атрибута витрине не нужна: карточка списка форматирует по ключу |
| Длинные атрибуты (>64 симв.) | «порядок ознакомления», «обременения» — абзацы | По ним не ищут. Правило по длине, а не список ключей: новый источник принесет свои имена полей |
| `pricePeriods` | 10% веса | График снижения показывает карточка лота, она предрендерена. Списку хватает `priceMin` |
| Хвост `description` после 240 символов | 24% веса | Опознавательная часть (модель, VIN, адрес) всегда в начале, дальше юридический текст |
| Все картинки, кроме обложки | | В списке видна одна |
| Контакты и СРО у сторон | | Для поиска нужны имя и ИНН, остальное — на карточке |
| `contentHash`, `firstSeenAt`, `sourceUrl`, `categoryName` | | Витрина их не показывает |

## Когда этот способ кончится

После подрезки — **212 байт на лот по проводу** (в gzip; GitHub Pages отдает
сжатым, поэтому считать надо именно так). Отсюда потолок:

| Лотов | Дамп | По проводу |
|---|---|---|
| 15 000 (МЭТС целиком) | 22 МБ | **3.0 МБ** — терпимо |
| 50 000 | 74 МБ | 10 МБ — больно, но работает |
| 100 000 | 147 МБ | 20 МБ — нельзя |

То есть способ живет примерно до **50 тысяч лотов**, а не до 10 тысяч, как
считалось раньше. Тогда же упрется и предрендер всех карточек. Дальше нужен
сервер, и не обход его отсутствия, а именно сервер — см.
[06-stack.md](06-stack.md).

Лимиты самого GitHub Pages: репозиторий до 1 ГБ, файл до 100 МБ, мягкий лимит
трафика 100 ГБ в месяц. Пока картинки лежат на источнике, упереться в них
трудно.
